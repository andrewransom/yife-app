# 04.5. Entity Enhancements Implementation Plan

## Purpose

Expand early entity types beyond the baseline entity shell with lightweight,
campaign-useful fields and child records.

This milestone sits between M04 entity creation and M05 rich text. It should make
Characters, NPCs, Parties, Factions, Locations, Storylines, Sessions,
Encounters, and Timeline Events useful as dense campaign reference objects
without turning Yife into a character sheet, monster builder, inventory system,
political simulator, map tool, project manager, session automation tool, combat
tracker, calendar engine, rules engine, or AI content tool.

This file is the implementation plan. The actual requirements, database spec,
user docs, and future media milestone updates are implementation tasks inside
this milestone. Do not update those documents before this plan is used unless
that task is part of the active implementation phase.

## Core Outcomes

- Replace Quest and Plot Arc as top-level concepts with Storyline.
- Add lightweight structured metadata for core entity types.
- Add campaign-configurable non-status option lists with preset packs.
- Add campaign palettes and symbols with preset packs.
- Add fixed system status lists for entity lifecycles.
- Add Character quick stats, NPC quick statblocks, and Encounter-local
  statblocks from campaign-editable templates.
- Add Character hooks/knives and simple promotion into Storylines.
- Add allowlisted field visibility for selected spoiler-prone header facts.
- Add entity-level core edit policy for typed/core fields.
- Preserve section/note prose boundaries and visibility rules.
- Keep all substantial long-form text in entity sections or notes.
- Keep all player-facing reads role-safe.
- Add downstream documentation work as explicit implementation phases.

## Non-Goals

- No full character sheet.
- No rules automation or D&D calculations.
- No inventory, equipment, spell, feature, action, initiative, round, or combat
  tracker modeling.
- No full NPC or monster builder.
- No full calendar engine.
- No arbitrary field-level permissions.
- No custom status editing.
- No external search.
- No realtime collaboration.
- No player-visible media handout workflow in this milestone.
- No production data migration compatibility work. The project is early and has
  no production data migration requirement.
- Do not preserve current `quest`, `plot_arc`, or `entity_option_definitions`
  APIs as active compatibility surfaces. Existing local schema, generated types,
  tests, composables, and UI references must be replaced as part of this
  milestone.

## Global Decisions

### Storyline Is Canonical

Use Storyline as the only top-level entity for quests, threads, and arcs.

- Remove `quest` and `plot_arc` as top-level current model concepts.
- Add `storyline` as a system entity type.
- A quest is a Storyline with `storyline_type = quest`.
- A narrative thread is a Storyline with `storyline_type = thread`.
- A plot arc is a major parent Storyline.
- Do not keep compatibility language in current requirements/specs except where
  needed to explain the replacement during this implementation.

Replacement scope:

- Replace `quests` and `plot_arcs` typed tables, creation inputs, summary fields,
  detail fields, seed data, RLS tests, generated types, composables, form fields,
  filters, labels, and UI copy with Storyline equivalents.
- Replace `related_plot_arc_entity_id` with `related_storyline_entity_id` where
  Encounter needs a direct structural Storyline link.
- Replace `quest_priority` with the Storyline priority option group.
- Remove or deactivate active `quest` and `plot_arc` entity types in local schema
  reset output; do not leave them createable, selectable, or exposed in generated
  frontend types except in obsolete migration history.
- Update smoke tests to prove no active create RPC, summary field, route option,
  filter option, or form path still depends on `quest` or `plot_arc`.

### Core Edit Policy

Add entity-level core edit policy for typed/core fields.

Allowed values:

- `gm_edit`
- `owner_edit`
- `player_edit`

Rules:

- Store on `campaign_entities` or an equivalent shared entity-policy table.
- Store enough ownership context to evaluate the policy. `core_edit_policy`
  alone is not sufficient.
- For Character core fields, the owner principal is `characters.controlling_user_id`.
- For private player-created Storylines, the owner principal is the creating user.
- For shared player-created Storylines, `player_edit` means active campaign
  members who can view the Storyline can edit its core fields.
- Campaign owners and GMs retain management capability unless an explicit field
  rule says otherwise.
- The helper/RPC that checks core editability must distinguish creator,
  controlling user, campaign owner, GM, and ordinary player.
- Sections keep their own edit policies.
- GM-created shared entities usually default to `gm_edit`.
- Characters default to `owner_edit` for owner-manageable core fields, with GMs
  retaining management capability.
- Shared player-created Storylines default to `player_edit`.
- Private player-created Storylines default to `owner_edit`.
- NPCs, Factions, Locations, Parties, Sessions, Encounters, and Timeline Events
  default to `gm_edit` unless the implementation explicitly allows otherwise.

### Visibility Values

Keep existing visibility values:

- `shared`
- `gm_only`
- `private`

Add:

- `character_owner_gm`

Rules:

- `private` remains author-only.
- `character_owner_gm` means the Character's controlling user plus campaign GMs
  and owner.
- Use `character_owner_gm` only for character-attached data where the controlling
  user relationship is explicit.
- Do not use generic `owner_gm` in MVP because ownership has multiple meanings in
  Yife.

### Allowlisted Field Visibility

Use explicit visibility columns for selected spoiler-prone typed fields.

Rules:

- Do not build arbitrary field-level permissions.
- Only fields allowlisted in this milestone get field visibility.
- Store visibility in dedicated columns beside the field, such as
  `leader_visibility`.
- Initial field visibility values are `shared` and `gm_only`.
- Raw typed tables that contain mixed-visibility fields must not be broadly
  player-readable.
- Player-facing reads for mixed-visibility typed data must use safe views/RPCs
  that omit hidden values and hidden structural-reference labels before data
  reaches frontend composables.
- Player-facing reads must omit hidden field values and avoid leaking through
  labels, counts, placeholders, filters, or related-record context.

Allowlisted field defaults:

- Faction `scope`: shared.
- Faction `numbers`: GM-only.
- Faction `leader`: GM-only.
- Faction `headquarters`: GM-only.
- Faction `territory`: shared.
- Location `accessibility`: shared.
- Location `population`: shared.
- Location `size_or_scale`: shared.
- Location `controlling_faction`: GM-only.
- Location `owner_or_steward`: GM-only.
- Location `ruler_or_authority`: GM-only.
- Location `danger_level`: GM-only.

### Apparent Versus True Facts

Use split fields only where apparent-vs-true is a real workflow.

Use split fields for:

- NPC apparent status and real status.
- NPC player-known location and GM true location.
- Faction public goal and GM true goal.

Use field visibility toggles for:

- Hiding or revealing a single true header fact.

Use sections/notes for:

- Rumors.
- Misinformation.
- Deception details.
- Explanations of why the party believes a falsehood.

### Media Fields In 04.5

Media columns may be added or retained for future-compatible entity metadata, but
04.5 does not implement upload, assignment, or player-facing handout workflows.

Rules:

- `image_asset_id`, `map_image_asset_id`, and `symbol_image_asset_id` fields are
  nullable and schema-only in 04.5 unless Milestone 10 upload/assignment work has
  already been implemented.
- Entity forms and detail UI must not expose upload or assignment controls for
  schema-only media fields.
- Safe read surfaces may include null media fields, but must not imply media is
  usable before M10.
- Any media field promoted before M10 must also include same-campaign asset
  validation, ready-asset filtering, public-by-URL warnings, and safe summary
  metadata.

### Summaries Versus Sections

Use short typed summaries for compact UI. Use sections for prose.

Rules:

- `public_summary` and `gm_summary` are short, plain-text fields where needed.
- Long descriptions, history, secrets, prep, observations, and narrative detail
  belong in `entity_sections` or `notes`.
- Do not add both typed `summary` and typed `description` unless a concrete UI
  needs both. In this milestone, typed long descriptions are not needed.

### Statuses Are System-Only

Statuses are seeded system values. Do not build custom status editing in MVP.

Seed exact status lists:

```text
character: active, retired, dead, missing, inactive
character_hook: unused, seeded, active, resolved, retired
party: active, inactive, disbanded, former, temporary
npc apparent/real: alive, dead, missing, unknown, inactive
faction: active, inactive, collapsed, unknown
location: active, ruined, abandoned, destroyed, unknown
storyline: open, active, completed, resolved, failed, abandoned
session: planned, completed, cancelled
encounter: planned, ready, completed, skipped, archived
resource: active, inactive, lost, consumed, archived
```

Timeline Events do not need a lifecycle status in this milestone.

Do not use `hidden` as a status. Hiddenness is visibility.

Storyline filter groups:

```text
Open: open, active
Finished: completed, resolved, failed, abandoned
Successful: completed, resolved
Unsuccessful: failed, abandoned
```

### Campaign Options

Replace `entity_option_definitions` with a generic campaign option model.

Use it for all non-status dropdown metadata touched by this milestone, unless a
field is explicitly free text.

Rules:

- Campaign options are campaign-owned rows.
- Presets are templates.
- Selecting preset options copies them into campaign-owned option rows.
- Copied rows keep source references for traceability and future update/import
  flows.
- Build one generic option-list manager for all non-status option groups touched
  by 04.5.
- The settings UI may group advanced lists, but it should use one reusable
  pattern, not bespoke editors.
- Statuses remain separate and system-only.
- Enforce or validate the expected option group for every typed option reference.
  A plain foreign key to `campaign_options(id)` is not enough.
- Create/update RPCs must reject options from the wrong campaign, wrong group, or
  inactive rows where the field requires an active selectable value.
- Existing records may continue to display deactivated option rows they already
  reference.
- Add unique constraints for campaign option group keys per campaign and option
  keys per group.

### Preset Packs

Support both broad preset packs and individual group presets.

Rules:

- Campaign creation offers preset pack selection.
- D&D Fantasy can be default/recommended, but the model remains system-agnostic.
- Users can select all or some preset options.
- Preset choices copy selected options into the campaign.
- Preset import must copy palette colors and symbols before options that reference
  default palette/symbol keys.
- If an option preset references a palette color or symbol that was not selected
  or could not be copied, the copied option keeps a null default reference rather
  than pointing across campaign/preset boundaries.
- Later campaign settings can import additional preset options.

Example future packs:

- D&D Fantasy.
- Generic Fantasy.
- Superhero.
- Blank/custom.

Only the D&D-friendly/default pack must be good enough for MVP unless another
pack is explicitly promoted.

### Campaign Palettes

- Palette presets copy into campaign-owned palette rows.
- Palette colors must carry enough metadata for accessible dense UI.
- Add unique constraints for palette color keys per campaign.
- Create/update RPCs must reject palette colors from the wrong campaign or

- Existing records may continue to display deactivated palette colors they

### Quick Stat Templates

Character quick stats and NPC/Encounter quick statblocks are
campaign-configurable templates copied from presets.

Rules:

- One active Character quick stat template per campaign for MVP.
- One active NPC/Encounter quick statblock template per campaign for MVP.
- Templates are editable by campaign owner/GMs.
- No formulas.
- No automatic calculations.
- No rules engine.
- Values are manually edited.
- Store values row-per-stat/field, not JSONB blobs.
- Enforce one active template per `template_kind` per campaign for MVP.
- Values must match their field value type: number fields use `value_number`,
  text fields use `value_text`, and the other value column stays null.
- Use unique constraints to prevent duplicate value rows for the same entity and
  field, and for the same encounter statblock and field.
- Template fields should be deactivated, not hard-deleted, once values may
  reference them.
- Existing values for deactivated fields remain readable to authorized users so
  old Characters, NPCs, and Encounter statblocks do not silently lose context.

Suggested schema sketch:

```text
campaign_quick_stat_templates
- id
- campaign_id
- template_kind -- character | npc_statblock
- label
- is_active
- source_preset_template_id nullable
- created_by
- updated_by
- created_at
- updated_at
```

Preset template rows should exist for quick stats/statblocks, following the same
copy-from-preset approach as option, palette, and symbol presets.

```text
campaign_quick_stat_fields
- id
- campaign_id
- template_id
- key
- label
- compact_label
- value_type -- number | text
- default_visibility
- min_value nullable
- max_value nullable
- sort_order
- is_active
- created_by
- updated_by
- created_at
- updated_at
```

```text
entity_quick_stat_values
- id
- campaign_id
- entity_id
- field_id
- value_number nullable

- created_by
- updated_by
```

Character quick stat visibility:

- Default to `character_owner_gm`.
- Do not expose party-wide stats by default.
- Template visibility can support future shared stats, but MVP presets should not
  make character mechanics visible to the whole party by default.

NPC/Encounter quick statblock visibility:

- Always GM-only in MVP.
- Player-facing capability information belongs in summaries, sections, or notes.

## Entity Implementation Details

### Campaigns

Add campaign-level fields/settings:

- `vtt_url` nullable URL for quick access to Roll20, Owlbear Rodeo, Foundry, or
  similar virtual tabletop links.
- `timezone` for session local time interpretation.

Campaign creation:

- Include preset pack selection.
- Default/recommend a D&D-friendly pack.
- Copy selected option, palette, symbol, and quick-stat presets into campaign
  rows.

### Characters

Character means player character.

Add or retain fields:

- `name`
- `status_id`
- `controlling_user_id`
- `image_asset_id`
- `species_ancestry_text` nullable free text.
- Character class progression child rows:
  - class name free text
  - optional subclass free text
  - level
  - sort order
- `pronouns` nullable text.
- `public_summary` nullable short text.
- `gm_summary` nullable short text.
- `character_sheet_url` nullable URL, shown in UI as "Character Sheet".

Media note:

- `image_asset_id` remains nullable and may be schema-only until Milestone 10
  implements upload, assignment, safe summary metadata, and public-by-URL
  warnings.

Do not add `temporarily_absent` as a character status. Absence can be derived
from session/attendance context later if needed.

Use aliases for:

- Aliases.
- Former names.
- Titles.

Character quick stats:

- Use the active campaign Character quick stat template.
- Store values row-per-stat.
- Default visibility is `character_owner_gm`.
- Put quick stats near the top of Character detail.
- Use compact inline editing where appropriate.

Character hooks/knives:

Add child records.

```text
character_hooks
- id
- campaign_id
- character_entity_id
- description_text
- status_id
- category_option_id nullable
- visibility
- gm_note_text nullable
- promoted_storyline_entity_id nullable
- sort_order
- created_by
- updated_by
- created_at
- updated_at
- deleted_at nullable
```

Rules:

- Description is plain text, not rich text.
- GM note is plain text.
- Hook categories use campaign options.
- Hook statuses are fixed system statuses.
- Visibility supports `gm_only`, `character_owner_gm`, and `shared`.
- Secret twists belong in GM note or GM-only hooks, not shared descriptions.
- Hooks remain attached to the Character even when promoted.

Promotion:

- Implement a simple "promote to Storyline" action.
- The action creates a Storyline prefilled from the hook.
- The action links the hook to the new Storyline through
  `promoted_storyline_entity_id`.
- Promotion should be transactional.
- Promotion must not copy `gm_note_text` into player-visible Storyline fields.
- If the hook is `gm_only`, the promoted Storyline defaults to `gm_only` and
  `gm_edit`.
- If the hook is `character_owner_gm`, the promoted Storyline defaults to
  `private` and `owner_edit` for the controlling user when the controlling user
  triggers promotion, otherwise `gm_only` and `gm_edit`.
- If the hook is `shared`, the promoting user chooses shared or private when
  permitted; shared player-created Storylines default to `player_edit`.
- Re-promoting an already promoted hook must be blocked or must return the
  existing linked Storyline without creating a duplicate.
- Do not build a full promotion wizard.

Default Character sections:

- Details
  - Renamed from Player Summary.
  - Shared/player-visible.
  - Canonical longer Character description.
- Backstory
  - `character_owner_gm` by default.
  - Owner-editable.
  - Can be shared later if visibility controls allow.
- GM Notes
  - GM-only.
  - GM-editable.
- Journal
  - Owner-only/private by default.
  - Owner-editable.
  - Used for personal character thoughts, reminders, and subjective notes.

Do not add default Character sections for appearance, personality, goals, or
relationships in this milestone.
